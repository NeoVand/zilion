## Analysis

### What was run

All 256 opcode files of SingleStepTests/65x02 `6502/v1` (10,000 tests each), as pinned for the second-machine test:
commit `2f6980a2d95757486c7bee24355c360e40e2a224`. The ledger records each file's SHA-256 and a digest over all of
them, so this baseline names its exact inputs. The vectors are emulator-generated, not captured from a chip
(Algocell `planning/ISA_RESEARCH_2026-10-10.md` §3); they are the reference here because no hardware-captured NMOS
set exists.

One test is one `m6502_step()`: one instruction, from the vector's initial state and RAM. The core is the text
`HOST_CONTRACT_PRELUDE_WGSL + M6502_CORE_WGSL` (every hook off), whose SHA-256 is in the Provenance table and in
`test/vectors/6502/expected-0.3.0-dev.json`.

### Result

**Every test matches in every compared field: 2,560,000 of 2,560,000, with no expected-divergence rules.** The rules
file is empty; nothing is explained away.

### What is compared

| Field | How | Architectural |
|---|---|---|
| `pc s a x y p` | `expected XOR actual`, masked to the width | yes |
| `halted` | not in the vectors; expected 3 (trap) for the 12 JAM opcodes, 0 for every other opcode | yes |
| `mem` | every listed address's final value; a write outside the listed addresses; a read of an address the vector does not list | yes |
| `bus` | the sequence of memory writes against the vector's `cycles` entries marked `write`: count, order, addresses, values | yes |
| `ports` | the 6502 has no port I/O; always empty | yes |
| `trap` | not in the vectors; passed through (input to output), declared in the rules file | no |

- **JAM-PC.** Zilion parks PC on a JAM opcode (as it parks every halting instruction); the vectors leave it one past.
  When the core reports the trap halt the adapter reports PC + 1. It did so in exactly the 120,000 tests of the 12
  JAM files (`mapped jam_pc`, per-opcode ledger). The compared `halted` field keeps a missing or a spurious halt
  visible, which the self-test's `jam-not-halting` and `nop-halts` mutants confirm.
- **Read-modify-write writes twice.** The `bus` field is how the old-value write is checked: the final RAM is the
  same with or without it. The 660,000 tests of the 66 read-modify-write opcodes (24 documented: ASL ROL LSR ROR
  DEC INC on memory; 42 undocumented: SLO RLA SRE RRA DCP ISC) match the reference's two writes, as do BRK's three
  pushes and JSR's two.
- **Not compared.** Cycle timing (Zilion is not cycle-accurate) and the reference's dummy *reads*. The core does not
  make dummy reads, because a read has no effect in a Zilion world and only instruction-stream fetches are hooked.
  A read of an address the reference never touched shows (`mem` unlisted-read), because the vectors list every
  address the reference touched; a read of an address it touched, even only by a dummy read, does not, and the
  order of reads is not checked. A wrong read usually shows as a wrong value.

### The unstable opcodes: constants the vectors encode

| Opcode | Behaviour pinned | How it was fixed |
|---|---|---|
| ANE (XAA) `8B` | `A = (A \| 0xEE) & X & imm` | 0xEE is the only magic value consistent with all 10,000 tests (every value 0x00–0xFF tried) |
| LXA (ATX) `AB` | `A = X = (A \| 0xEE) & imm` | the same: 0xEE is the unique fit |
| SHA `93`, `9F` | stores `A & X & (H + 1)` | H = high byte of the base address before indexing; on a page crossing the stored value also replaces the high byte of the target address |
| SHX `9E` | stores `X & (H + 1)` | as SHA |
| SHY `9C` | stores `Y & (H + 1)` | as SHA |
| TAS `9B` | `S = A & X`, stores `S & (H + 1)` | as SHA |
| LAS `BB` | `A = X = S = M & S` | |

Real chips vary in these (the magic constant depends on the chip and temperature; the `& (H + 1)` term drops out
when a DMA cycle interrupts the instruction). The values above are what the reference encodes, and a soup on this
core sees exactly them. They are constants of the `nmos` variant (`M6502_UNSTABLE` in `src/cores/m6502/core.wgsl.ts`).

### Where the vectors are thin

- **Decimal mode.** The decimal result is a function of (A, operand, C) alone, 131,072 inputs per operation. Each
  immediate file covers about 3.7% of them (ADC # `69`: 4,874 distinct inputs in its 4,962 decimal-mode tests;
  SBC # `E9` 4,822; `EB` 4,925; ARR `6B` 4,938). Pooled over every ADC and RRA file the independent reviewer counted
  57,050 of 131,072 (43.5%), and 59,837 for SBC and ISC. The mutant that takes decimal ADC's Z from the BCD result
  (the 65C02 rule) is caught by 34 of the 10,000 tests of `69`. As an informational cross-check (not a gate: its
  model is not a reference), the reviewer wrote a separate nibble-and-carry model of ADC, SBC and ARR, which agreed
  with every SST test of those operations, and ran the core on all inputs of `69`, `E9`, `EB` and `6B` (262,144
  each, both D values, random other P bits) and `0B`, `4B`, `CB` (65,536 each) against it: no difference. An
  exhaustive gate needs a reference for the remaining inputs (hardware, or the documented algorithm adopted as the
  specification); none is committed.
- **B and bit 5 of P.** Bit 5 is 1 in every test, and B is 1 only in the tests of 24 files (the JAMs, NOP abs,X,
  SHA/SHX/SHY/TAS); so no flag-writing instruction is tested with B = 1 or bit 5 = 0. Every flag update in the
  core keeps bits 4 and 5 (masks 0x7D, 0x3C, 0x7C, 0x3D, 0xFE), and only PHP, BRK, PLP and RTI touch them. A world
  can store bit 5 = 0 (`init.set`); that changes no behaviour (PHP and BRK push both bits set) and stays in the
  record until a PLP or RTI.

### What the vectors cannot check, and what does

- **Bus order on a small ring.** A vector has 64 KiB of distinct addresses; a soup's ring of 2L bytes aliases many
  of them, so the order of accesses inside one instruction becomes visible. The core keeps the chip's order: JSR
  pushes before fetching its high operand byte, BRK reads its vector after its pushes, RMW writes old then new.
  World tests (`test/world/cases_m6502.mjs`) pin each of these on rings of 32, 33 and 64 bytes with hand-computed
  expectations, and fail when the order is changed (checked by mutating the built core).
- **Hooks.** This baseline runs the core with every hook off. The self-test runs all 2,560,000 vectors again on the
  text with the fetch, instruction-start and trap hooks on and neutral (the text worlds with maps, dials or trap
  policies run): no divergence; with a trap hook that ignores JAM, every test of `02` diverges in `halted`, so the
  check is live. World tests add hook neutrality on random pairs, ring = mask, and the policies (JAM ignored,
  lethal first unit, ablation).
- **Interrupts.** There is no IRQ or NMI line in a Zilion world, so the B flag is always pushed set (by PHP and
  BRK); the vectors' B behaviour for PHP, BRK, PLP and RTI is matched.

### Mutants

The harness self-test plants 18 single-point bugs in the 6502 core and requires each to produce unexpected
divergences in the field it breaks: decimal ADC Z from the BCD result, decimal ADC V from the binary sum, decimal SBC
without the high-nibble adjustment, decimal ARR without its high fix-up, JMP ($xxFF) carrying into the high byte,
zp,X carrying into page 1, a (zp),Y pointer read from page 1, an RMW without its old-value write, an RMW writing the
new value twice, ANE magic 0xFF, LXA magic 0x00, SHA/SHX without the + 1, PHP pushing B clear, PLP loading B, BRK
through 0xFFFC, a JAM that does not halt, a NOP that halts, TXS setting flags. All 18 are caught.

### Determinism

The baseline was produced twice; both runs gave the ledger SHA-256 in the Provenance table. The self-test also
requires two sessions and repeated dispatches to agree, and the `sparse` and `full` memory models to give
identical 6502 ledgers.

### A note on test names

Test names are not unique within a file (168,695 repeated names in 232 files: the name is the instruction bytes).
`--test <name>` therefore selects every test of that name; the ledger's examples carry the name and the bytes.
